Yuxuan · AIML 515 · October 4, 2026

The most critical bug was a future window that looked exact but was not a matching transit. After the Seattle profile was saved, the strongest repeated pattern was Pluto square natal Saturn. That pair does not come within seven degrees in the next 18 months. The first search still printed April–May 2027, while the text below called the range a placeholder. A reader would trust the months. The corrected search uses an exact repeat when one exists. Otherwise it takes the tightest similar aspect from the same planet and says the match is partial. For this profile the window is October–December 2026, another Pluto square, not the Saturn pattern. The date is the claim of the page, so a made-up range was worse than a layout mistake.

The most important security issue was the database file, not a stolen API key. None were in the project. The file stores birth dates, birth times, cities, and life-event descriptions, and it was mode 644, so another account on this Mac could open it. The API now sets the file to mode 600 when it opens. The same pass stopped validation errors from echoing the typed sentence, marked personal JSON with Cache-Control: no-store, and refused an API host that is not this computer. A DROP TABLE string in an event stayed ordinary text, so SQL injection was tested and was not present.

I used the AI assistant to run a test list I would otherwise sample. It clicked Send, Restart, Analyze, Start Over, and Retry, including Retry while the API was blocked and again after it recovered. It sent odd answers: an ambiguous date, February 31, “yes” as a city, two dates, a future date, and “maybe” at confirmation. It checked four screen sizes and the unit tests, then changed the file mode and the error body. I checked the live responses myself. There is no login, which is reasonable only while the API stays on 127.0.0.1.
